**调试中的竞争假设。** 生成五个团队成员，每个调查关于应用在一条消息后退出的不同理论。让他们互相交流，反驳彼此的理论，就像科学辩论。这确实优于顺序调查，后者容易受到锚定效应的影响——一旦您探索了一个理论，后续调查就会偏向它。多个调查者进行对抗性辩论能更快地收敛到根本原因。
**不同视角的并行代码审查。** 一个团队成员关注安全影响，一个检查性能影响，一个验证测试覆盖率。单个审查者往往倾向于一次关注一种类型的问题。将审查标准拆分为独立领域意味着每个领域同时得到全面关注。
**跨层功能开发。** 涉及前端、后端和测试的变更——每个由不同的团队成员负责。不是一个智能体在层之间切换上下文，而是三个智能体并行工作，完全专注于各自的领域。
**研究与探索。** 多个团队成员同时调查不同方法，分享发现，并收敛到最佳前进路径。研究发现直接流入实现上下文——没有传话游戏。
您通过负责人的终端与智能体团队交互。实践中一些重要的控制功能：
两个选项。**进程内**（默认）：所有团队成员在您的主终端内运行。使用 `Shift+Up/Down` 选择团队成员并输入以直接发送消息。按 `Enter` 查看团队成员的会话，按 `Escape` 中断其回合，按 `Ctrl+T` 切换任务列表。适用于任何终端。
**分屏**：每个团队成员通过 tmux 或 iTerm2 拥有自己的窗格。您可以同时看到每个人的输出，并点击进入窗格直接交互。在设置中或按会话设置：
```
{
  "teammateMode": "tmux"
}
```
或为单个会话覆盖：
```
claude --teammate-mode in-process
```
对于有风险的工作，要求团队成员在实施前制定计划。团队成员在负责人批准其方法之前以只读模式工作：
生成一个架构师团队成员来重构认证模块。
要求在他们进行任何更改之前获得计划批准。
如果被拒绝，他们会修改并重新提交。您可以通过标准影响负责人的判断："仅批准包含测试覆盖率的计划"或"拒绝修改数据库模式的计划"。
按 `Shift+Tab` 将负责人限制为仅协调——生成、发送消息、关闭团队成员和管理任务。不接触代码。这阻止了一个常见问题：负责人分心并自己实现功能，而不是等待团队成员。
每个团队成员都是一个完整的 Claude Code 会话。您可以直接向任何团队成员发送消息以提供额外指令、提出后续问题或重定向其方法——无需通过负责人。
共享任务列表协调整个团队的工作。任务有三种状态：待处理、进行中和已完成。任务可以依赖其他任务——具有未解决依赖关系的待处理任务在依赖项完成之前不能被认领。当阻塞任务完成时，自动解除阻塞发生。
负责人可以明确分配任务，或者团队成员可以在完成后自行认领下一个未分配、未阻塞的任务。任务认领使用文件锁定来防止竞态条件。
团队和任务存储在本地：
```
~/.claude/teams/{team-name}/config.json    # 团队元数据 + 成员
~/.claude/tasks/{team-name}/               # 任务列表
```
团队成员可以读取配置文件以发现其他团队成员。
要求负责人关闭特定的团队成员——他们可以批准或拒绝请求并附上解释。要清理整个团队：
```
清理团队
```
始终使用负责人进行清理。团队成员不应运行此操作，因为他们的团队上下文可能无法正确解析，可能使资源处于不一致状态。负责人检查是否有活跃的团队成员，如果仍有运行中的则失败，因此先关闭他们。
我不断回到这一点：[使某人成为优秀工程管理者的技能](https://addyosmani.com/blog/coding-agents-manager/)直接转化为有效的智能体编排。智能体团队使这一点更加明确。
**任务大小很重要。** 太小则协调开销占主导。太大则团队成员工作时间过长而没有检查点，存在浪费精力的风险。最佳点是产生清晰可交付成果的独立单元。每个团队成员 5-6 个任务能让每个人保持高效，并让负责人在有人卡住时重新分配工作。
**文件所有权很重要。** 两个团队成员编辑同一文件会导致覆盖。分解工作，使每个团队成员拥有不同的文件集。与人类团队设定相同的边界，以避免合并冲突。
**上下文加载很重要。** 团队成员会自动获取您项目的 `CLAUDE.md`、MCP 服务器和技能，但他们不会继承负责人的对话历史。在生成提示中包含任务特定的细节：
生成一个安全审查员团队成员，提示为："审查
src/auth/ 处的认证模块是否存在安全漏洞。重点关注
令牌处理、会话管理和输入验证。该应用
使用存储在 httpOnly cookie 中的 JWT 令牌。报告任何问题并附上
严重性评级。"
简报越具体，输出越好。一如既往——但现在您是在为团队编写简报，而不是单个智能体。
这是实验性的。粗糙的边缘是真实存在的，值得了解。
**负责人有时会自己实现而不是委派。** 告诉它等待："在您的团队成员完成任务之前等待。"或使用委派模式（`Shift+Tab`）将负责人限制为仅协调工具。
**进程内团队成员无会话恢复。** `/resume` 和 `/rewind` 不会恢复进程内团队成员。恢复后，负责人可能尝试向不再存在的团队成员发送消息。生成新的。
**任务状态可能滞后。** 团队成员有时未能将任务标记为已完成，从而阻塞依赖任务。检查工作是否实际完成，并提示负责人或手动更新。
**每会话一个团队，无嵌套团队。** 负责人一次管理一个团队。团队成员不能生成自己的团队或团队成员。只有负责人管理团队。这是有意为之——防止无限递归、失控的令牌成本和[人类监督](/agentic-engineering/human-in-the-loop/)的缺失。在开始新团队之前清理当前团队。
**令牌成本随团队成员数量扩展。** 每个团队成员是拥有自己上下文窗口的独立 Claude 实例。对于常规任务，单个会话更具成本效益。多智能体模式在更大、可并行化的工作上才有回报——而不是用于修复拼写错误。
**分屏需要 tmux 或 iTerm2。** VS Code 的集成终端、Windows Terminal 或 Ghostty 不支持。默认的进程内模式在任何地方都有效。
**权限从负责人传播。** 所有团队成员从负责人的权限设置开始。如果负责人使用 `--dangerously-skip-permissions` 运行，所有团队成员也是如此。您可以在生成后更改单个团队成员的模式，但不能在生成时设置每个团队成员的模式。
**关闭可能很慢。** 团队成员在关闭前完成当前请求或工具调用，这可能需要时间。
看着智能体并行工作有一种诱人的魅力。活动指标令人印象深刻——每小时提交数、并行任务完成数、接触的代码行数。
但活动并不总是转化为价值。
多智能体系统的风险在于，它们使得快速生成大量代码变得容易。这些代码仍然需要正确、可维护，并且实际解决问题。我见过开发者迷失方向，花更多时间配置编排模式而不是思考他们在构建什么。
**让问题引导工具，而不是反过来。** 如果聚焦会话中的单个智能体能更快地达到目标，就用那个。如果您需要并行专家，就用智能体团队。智能体团队增加了协调开销，并且使用的令牌比单个会话多得多。它们在团队成员可以独立运作时效果最佳。对于顺序任务、同一文件编辑或具有许多依赖关系的工作，单个会话或子智能体更有效。
如果您想要围绕智能体团队更结构化的工作流，Every 的[复合工程插件](https://github.com/EveryInc/compound-engineering-plugin)可能值得一看。它是 Claude Code 的一个插件，添加了专门的审查智能体和一个计划→工作→审查→复合循环，其设计理念是每个工程工作单元应使后续单元更容易。
直接在 Claude Code 中安装：
```
/plugin marketplace add https://github.com/EveryInc/compound-engineering-plugin
/plugin install compound-engineering
```
与智能体团队最相关的部分：`/workflows:plan` 将功能想法转化为详细的实现计划（正是使智能体委派有效的那种前期规范），`/workflows:review` 在合并前运行多智能体代码审查（安全性、性能、架构和复杂性——每个都有专门的审查员），`/workflows:compound` 记录学习成果，使未来的智能体受益于过去的工作。
最后一点是最有趣的。该插件的理念——80% 的规划和审查，20% 的执行——清晰地映射到使智能体团队有效的要素上。您的规范越好，智能体输出就越好。您编码的学习成果越多，每个后续智能体就越少徒劳挣扎。这是我在[AGENTS.md 和持久上下文](https://addyosmani.com/blog/self-improving-agents/)中描述的相同复合动态，但打包成了可重复的工作流。
如果您不只在 Claude Code 中使用，它还可以与 OpenCode 和 Codex（实验性）配合使用。
如果您是新手，从小的开始。
**从研究和审查开始。** 具有清晰边界且不需要编写代码的任务——从三个角度审查 PR、研究库、用竞争理论调查错误。这些展示了并行探索的价值，而没有并行代码变更的协调复杂性。
**然后尝试跨层功能。** 前端、后端和测试各由不同的团队成员负责。清晰的边界，明确的可交付成果。
**然后扩展到更大的重构。** 多个服务，在共享设计阶段后并行实现。这是时间压缩变得显著的地方——可能需要数天的顺序工作压缩为几小时的并行执行加审查。
核心技能不是编写更少的代码。而是**将问题分解为智能体团队可以执行的结构**——知道构建什么，正确性意味着什么，以及如何验证结果。实现越来越成为足够精确规范的问题。
这就是当智能体能够实际协调时[智能体工程](https://addyosmani.com/blog/agentic-engineering/)的样子。协调 AI 智能体系统的架构就在这里。明智地使用它。
完整的 [Claude Code 智能体团队文档](https://code.claude.com/docs/en/agent-teams)包含完整的设置和使用指南。
